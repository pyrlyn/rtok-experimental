# Агенти й worktree

Кожна сесія агента, що працює через rtok, отримує один **id агента rtok**, а кожен worktree прив'язаний до агента, який ним володіє, однаково на кожному хості. Агенти й користувач можуть надсилати одне одному повідомлення за цим id. Ця сторінка — опис для користувача (рішення D34); таблиці встановлення для кожного хоста є в [agents.md](agents.md), а ключі конфігурації — в [config.md](config.md).

## Id агента

- Id — це випадковий UUIDv4, який rtok видає сам; він показується першими 8 символами й приймається будь-де як будь-який унікальний префікс завдовжки 4 символи або більше. Id сесій хостів не унікальні між хостами, а кілька хостів їх узагалі не мають, тому їх ніколи не використовують як id.
- **Хуки** реєструють агента на першій події сесії й оновлюють його на кожній наступній (`SessionStart`, виклики інструментів, `SessionEnd`). Хосту, чиє встановлення несе хуки, більше нічого не потрібно.
- **MCP** обслуговує хост без хуків. `rtok mcp --host <host>` прив'язується до агента сесії за власним id сесії хоста, якщо хост кладе його в середовище (Grok Build: `GROK_SESSION_ID`), інакше — за єдиним живим агентом цього хоста в тому самому каталозі, якого бачили після запуску процесу. Два кандидати нікого не прив'язують, тож повідомлення ніколи не потрапляє не до того агента. Хост, який не може нести ні хуків, ні id сесії, отримує власний рядок, який реєструє процес MCP.
- Агент завжди береться із сесії. Жоден інструмент не приймає аргументу агента чи власника, тож модель не може заявити права на worktree або надіслати повідомлення від імені іншого агента.
- `rtok agents whoami` виводить id (`RTOK_AGENT_ID`, який хук Claude Code кладе в середовище сесії й наводить у рядку контексту початку сесії; якщо його немає, як у десктопному застосунку Claude, — агент сесії з `CLAUDE_CODE_SESSION_ID`); MCP `whoami` повертає його разом зі способом прив'язки.

## Бачити агентів і говорити з ними

| Команда | Інструмент MCP | Що робить |
| --- | --- | --- |
| `rtok agents sessions [--all]` | `agents_list` | кожен агент із хостом, станом (`live`, `idle`, `ended`), активністю, статусом, заявленими worktree і кількістю непрочитаних; `--all` додає завершених |
| `rtok agents show <id>` | `agent_show` | один агент: хост, модель, id, батько й субагенти, cwd, заявлені worktree, статус, непрочитані |
| `rtok agents status <text>` | `agent_status_set` | чим зайнятий цей агент (не більше 120 символів); порожній текст очищає його |
| `rtok agents send <id> <text>` | `agent_send` | повідомлення одному живому агенту (з обмеженням розміру); `--all-live` надсилає кожному живому агенту проєкту відправника; `--task <id>` (`task` у MCP) позначає повідомлення завданням, про яке воно, наприклад `A12` |
| `rtok agents inbox [<id>]` | `agent_inbox` | ваші власні повідомлення, від найстаріших, позначаються прочитаними; з id — черга цього агента, нічого не позначається; `--task <id>` (`task` у MCP) читає листування за одним завданням, решта лишається непрочитаною |

`[agents] idle` (типово 30 хвилин) визначає, хто живий. `[agents] enabled = false` зупиняє реєстрацію та надсилання.

### Повідомлення

- Хост із хуками отримує нові повідомлення, **надіслані** в наступний промпт або результат інструмента, в оформленому вигляді й у межах `[agents] push_bytes`; решту оголошено як `… and N more`, її читають через `agent_inbox`. Кожен інший хост **забирає** їх сам: рядок початку сесії каже викликати `agent_inbox`, а повідомлення читає інструмент MCP або `rtok agents inbox`.
- Безпека: тіло повідомлення — це текст від іншого агента чи людини, а не інструкція. Кожне приходить усередині фіксованої рамки, що називає id відправника, керівні символи вилучено, розмір обмежено, і жоден аргумент інструмента не може назвати відправника. Сприймайте його як інформацію.

## Worktree

Сирий `git worktree` не записує власника, вік чи розмір. `rtok worktree` дає кожному worktree одне розташування, одну назву, одного власника й одного агента:

| Команда | Інструмент MCP | Що робить |
| --- | --- | --- |
| `rtok worktree add <task> [<slug>]` | `worktree_add` | створює `<root>/<repo>-<task>` на гілці `<task>[-<slug>]` зі свіжого `origin/<default>`, заблокований як `<owner> \| <task> \| <date> \| agent <uuid>`, і записує заявку |
| `rtok worktree adopt [<path>] [--task <id>]` | `worktree_adopt` | прив'язує worktree, створений хостом, до викликаного агента; каталог лишається там, де його поклав хост |
| `rtok worktree claim <path>` | — | те саме для наявного worktree, який ви називаєте; переписує його блокування, коли його немає, воно вже ваше, або його агент завершився чи не був видимий довше за `--stale-lock` (`7d`) |
| `rtok worktree list` | `worktree_list` | кожен worktree репозиторію з власником, прив'язаним агентом і його станом, `origin`, розміром вихідників (`--sizes` обходить і білд-кеші); а також осиротілі, яких git більше не показує |
| `rtok worktree remove <path\|task>` | `worktree_remove` | видаляє ваш власний чистий worktree і його злиту гілку; відмовляє для брудного, незлитої гілки, того, у якому ви стоїте, і чужого блокування, окрім випадку, коли задачу завершено (злита, чиста, з власними комітами) або агент блокування завершився чи не був видимий довше за `--stale-lock` (`7d`); відмова називає, як давно бачили власника; ніколи не примушує |
| `rtok worktree finish [<path>]` | `worktree_finish` | передає worktree задачі на рев'ю: комітить залишок (`-m`, інакше `<task>: <slug>`), пушить гілку, відкриває PR або бере вже відкритий, просить squash auto-merge (`--no-auto-merge` пропускає; відмова — попередження), потім знімає блокування; відмовляє для основного checkout, detached HEAD, чужого блокування, файлів з обліковими даними на кшталт `.env` чи приватних ключів і гілки, якій нічого передати; задачу ніколи не закриває. `--repo <owner/name>`, коли `origin` не називає репозиторій. Коли гілку злито, запущений `rtok mcp` (перевіряє раз на 5 хвилин) закриває задачу rtok, потім видаляє чистий worktree, його гілку й прив'язку; не злитий або брудний лишається |
| `rtok worktree gc`, `clean` | — | прибирають завершені worktree, видаляють неактивні кеші збірки; пробні запуски, доки немає `--yes`; worktree живого агента зберігається, а якщо його задачу завершено й він простоює довше за `--idle`, його видаляють за будь-якого блокування; чуже блокування на злитому чистому worktree, якого не торкалися `--stale-lock` (`7d`), вважається покинутим |
| `rtok worktree migrate` | — | переносить worktree репозиторію, що лежать поза коренем, у `<root>/<repo>-<task>` (worktree без блокування зберігає назву каталогу) через `git worktree move`; блокування та claim переїжджають разом із ним; без `--yes` це пробний прогін; пропускає основний checkout, worktree, у якому ви стоїте, worktree з блокуванням чи claim іншого агента або з іншою живою сесією, worktree з підмодулями та зайнятий цільовий шлях |

Власник — це `<host> / <model>` агента, доки виклик CLI не передасть `--owner`; виклик MCP ніколи цього не робить. Без агента й без `--owner` (хук, що запускається раніше, ніж сесія отримала id агента) власник — це `RTOK_OWNER`, якщо змінну задано, інакше користувач ОС (`USER`, `USERNAME`, інакше `unknown`), і rtok пише попередження в stderr; таке блокування не називає агента, тож тримає, як будь-яке блокування без нього. Корінь — це `[worktree] root`, типово `.rtok/worktrees`: відносний корінь відлічується від основного checkout (і зсередини worktree теж), а перед першим worktree там rtok робить так, щоб git ігнорував `.rtok/`: у `.gitignore`, якщо він є в проєкті, інакше в `.git/info/exclude`. Відносний корінь, що виходить за межі проєкту, відхиляється; `~` і абсолютні корені означають те саме, що й раніше, а worktree, створені деінде, далі працюють. З `[worktree] enabled = false` rtok не чіпає worktree: кожна команда `rtok worktree` (і `list` теж) каже, що вони не ввімкнені, MCP не показує жодного інструмента `worktree_*`, а хуки `WorktreeCreate`/`WorktreeRemove` Claude Code і CodeBuddy роблять те, що хост робить без rtok. Command Code не має власного запасного шляху, тож його хук створення тоді робить простий worktree у `.commandcode/worktrees/<name>` на гілці `worktree-<name>` — так само, як коли rtok відхиляє назву.

Новий worktree починає з прогрітими кешами збірки. Після `git worktree add` rtok заповнює кожен запис `[worktree] seed_dirs` (типово `target` і `node_modules`; голе ім'я збігається й на рівень нижче, тож `web/node_modules` теж рахується) із сусіднього checkout того самого репозиторію, який збирав його останнім. Кожен файл — copy-on-write клон, де файлова система вміє ділити блоки (APFS на macOS; btrfs, XFS і bcachefs на Linux; ReFS і Dev Drive на Windows), тому навіть багатогігабайтний `target/` майже не займає місця, а деінде — звичайна копія, яка заощаджує збірку, але не диск. Кожен файл зберігає час зміни джерела, тому cargo перезбирає те, що змінила нова гілка, і лишає всі залежності; `touch` не потрібен. Місце, яке в checkout уже зайняте (відстежуваний каталог, попередній засів), не чіпається, а посилання ніколи не буває джерелом. Засів робиться за можливості: у разі помилки виводиться попередження, часткова копія видаляється, а worktree однаково створюється. `rtok worktree add --no-seed` пропускає його один раз; `[worktree] seed = false` вимикає його, зокрема для MCP `worktree_add` і хука Claude `WorktreeCreate`. Він виконується до повернення команди, тому великий кеш, який доводиться копіювати, а не клонувати, займає стільки ж часу, скільки копіювання.

`worktree add` працює за принципом «все або нічого». Перед запуском git він перевіряє вільне місце на томі, де з'явиться робоче дерево, і одним рядком відмовляє, якщо вільно менше за `[worktree] min_free_mib` (типово 2048 МіБ; 0 вимикає перевірку). Якщо після цього щось падає (git, наприклад з `No space left on device`, або запис claim), rtok видаляє каталог, гілку й claim, створені цим викликом; гілка чи каталог, що існували до виклику, лишаються.

`worktree add` приймає завдання та назву гілки і одним аргументом: `rtok worktree add "T504 read-hook-same-path"` — це завдання `t504` на гілці `t504-read-hook-same-path` (перше слово — id, решта — slug, пробіли стають дефісами). Якщо worktree цього завдання вже є і заблокований тим самим власником (або агентом), команда друкує його шлях і нічого не змінює, тож повтор уже виконаного add безпечний; worktree, який тримає хтось інший, як і раніше відхиляється.

### Worktree, які хост створює сам

Хост, що створює worktree у власному пулі (Cursor, Codex, Windsurf і Devin, Kilo, Claude Code, Conductor), не лишає rtok вибору місця. Запустіть `worktree_adopt` (або `rtok worktree adopt`) усередині нього: rtok виводить `origin` зі шляху, бере завдання з `--task`, інакше зі старого блокування, інакше з гілки, і прив'язує його.

- Cursor, Codex і Windsurf/Devin самі видаляють worktree, щоб не перевищити ліміт (приблизно 25, 15 і 20). Чи переживає блокування git таке видалення, не підтверджено, тож прийняття там записує заявку лише в сховищі rtok і не пише блокування.
- Кожне інше походження отримує те саме блокування v2, що й `worktree_add`.
- Worktree, заблокований кимось іншим, не береться, поки його агент у межах `--stale-lock` (`7d`). Завершений агент або агент, якого сховище не бачило довше за це вікно, не заважає `claim` і `adopt`; відмова називає, як давно бачили власника. Блокування без агента або з агентом, якого сховище не знає, і далі тримає worktree.
- Запуск `adopt` зі скрипта після створення в хості (Cursor `.cursor/worktrees.json`, Kilo `.kilo/setup-script`, Windsurf і Devin `post_setup_worktree`) — налаштовується командою `rtok agents install <host> --project` (хости `cursor`, `kilo`, `windsurf`, `devin`): вона додає один запис у файл проєкту й нічого більше не чіпає; `rtok agents uninstall <host> --project` його прибирає. Без названого агента `adopt` прив'язує єдиного живого агента хоста цього пулу, чий робочий каталог — репозиторій, а якщо таких немає або їх кілька, відкладає claim без агента й без git-блокування; його завершує наступний `adopt` або `SessionStart` сесії, що працює всередині worktree; `worktree gc` такий worktree не чіпає. Через skill нижче агент може прийняти worktree завжди.

Skill `worktrees` розповідає агентові все це: `worktree_add` для нової роботи, `worktree_adopt` для worktree, створеного хостом, `worktree_finish`, коли задачу виконано, `worktree_remove`, коли злито.

Кожен хост може створювати worktree через `worktree_add` (MCP) або `rtok worktree add` (CLI); хост без рядка агента може передати `--owner` у CLI, інакше власника обирають, як описано вище. Worktree, чий шлях не збігається з жодним із пулів вище, показується з origin `other` і приймається так само. `worktree add` також записує `env.CLAUDE_CODE_TASK_LIST_ID` = `<project>-<task>` у `.claude/settings.local.json` нового worktree, щоб сесії Claude Code там ділили один список завдань; записується лише цей ключ, решта файлу не змінюється, файл, що не є коректним JSON або вже задає цей id, лишається недоторканим із попередженням, а `.claude/` ігнорується git.

### Десктопний застосунок Claude

У вкладці Code десктопного застосунку MCP-інструменти rtok обслуговує один `rtok mcp`, який застосунок запускає з `claude_desktop_config.json` для всіх сесій одразу, а не процес самої сесії. Цей процес не перебуває під жодною сесією і в жодному її каталозі, тому MCP `whoami`, `worktree_*` і `agent_*` не можуть визначити, який агент їх викликав, і відповідають «not linked to an agent session» з цією причиною. Там використовуйте `rtok agents` і `rtok worktree` з shell агента. Щоб спільний запис не приховував власний сервер сесії — задача T456.
