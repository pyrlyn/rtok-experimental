# Бенчмарки — инструкции для агентов

После **любого** запуска бенчмарка (теста фикстур `tests/bench_fixtures.rs`, Docker/Colima-обвязки `bench/harness/run.py`, сравнения с конкурентом) в том же изменении обновите все места, где встречаются старые числа. Нет измерения — нет утверждения: для отсутствующего измерения указывайте `no data`, никогда не оценивайте его.

## 1. Запуск

Всегда в Docker, никогда на физической машине.

1. Colima (macOS): используйте профиль `rtok-bench` (4 CPU, 8 GiB). Укажите `DOCKER_HOST` как сокет профиля (`~/.colima/rtok-bench/docker.sock`); если сбоит помощник учётных данных, укажите в `DOCKER_CONFIG` каталог с пустым `credsStore`.
2. Обвязка: `python3 bench/harness/run.py rtk --rtok-ref origin/main --rtok-pr origin/<branch>`. Ссылки должны разрешаться в вашем клоне (`origin/...`, а не просто имя ветки). Запуск длится 10 минут и больше: выполняйте его в фоне и дождитесь завершения; при закрытии shell процесс остановится.
3. Результаты сохраняются в `bench/harness/results/<tool>/<stamp>/` (`results.json`, `summary.md`, `negatives.txt`, `versions.json`, `samples/`). Они хранятся в репозитории.
4. Тест фикстур: `cargo test --test bench_fixtures`. В контейнере передайте исходники командой `tar --no-xattrs … | docker cp - <container>:/src` (расширенные атрибуты macOS ломают обычный `docker cp`; bind-mount `/tmp` не сработал).
5. Обновляйте фикстуры только по настоящему захвату данных: `run.py rtk --refresh-fixtures <dir>`, затем копируйте их в `tests/fixtures/bench`. Не редактируйте их вручную. После обновления проверьте каждый `min_savings_pct` в `case.toml`.
6. Версии конкурентов закреплены в Dockerfile конкурента в `bench/harness/tools/`.
7. Диск: виртуальная машина Colima и каталоги Rust `target` быстро заполняют диск. Собирайте внутри контейнера и удаляйте созданные контейнеры и временные каталоги после завершения.

## 2. Где находятся числа

Ищите, не угадывайте: `rg -n "<old number>|bench/harness/results" README.md docs/`.

- `docs/comparison/rtok-vs-<tool>.md` — отдельная страница для каждого конкурента.
- `docs/comparison/README.md` — перечень со статусом каждого конкурента.
- `docs/comparison.md` — сводные таблицы.
- `docs/research/competitors-techniques.md` — пробелы и цели (цели не являются измерениями).
- `plan.md` / `todo.md` — строки задач с целевыми значениями.
- `README.md` — основные показатели, если они там есть (на момент написания их не было).
- `bench/harness/README.md` — команда воспроизведения и правила честного сравнения, если менялись флаги.
- `docs/ru/`, `docs/uk/` — переводы; поддерживайте их в соответствии с оригиналом (см. `CONTRIBUTING.md`).

## 3. Структура страницы (блоки сайта)

На каждой странице сравнения должны быть такие разделы `##` в указанном порядке:

1. **Что изменилось** — дата запуска, SHA rtok, отличия от предыдущего запуска.
2. **Показатели производительности** — итоги по каждой команде: raw, rtok main, rtok PR, rtok PR `--no-ref`, конкурент.
3. **Таблица команд** — отдельная таблица `###` для каждой команды, по одной строке на случай.
4. **Где rtok выигрывает / проигрывает** — пункты со значениями; укажите каждую строку `WARN NEGATIVE` и отметьте случаи `nondet!`.
5. **Методология** — SHA фикстур, версии инструментов, токенизатор, количество запусков, каталог результатов.
6. **Конкуренты в целом** и **Как повторить**.

## 4. Контрольный список

- [ ] Запуск выполнен в Docker; путь к каталогу результатов записан.
- [ ] `cargo test --test bench_fixtures` проходит.
- [ ] `negatives.txt` прочитан; каждый отрицательный результат указан в разделе «Где rtok выигрывает / проигрывает».
- [ ] Старые числа найдены поиском и заменены во всех файлах из раздела 2.
- [ ] SHA и версии инструментов совпадают с `versions.json`.
- [ ] Задержка не представлена как скорость фильтрации (основную долю вносит shim воспроизведения).
- [ ] Английский оригинал обновлён; переводы ru/uk синхронизированы или добавлены в список последующих задач.
- [ ] Временные каталоги и контейнеры удалены.
