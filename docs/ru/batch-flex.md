# Batch, Flex и маршрутизация

rtok — это промежуточный слой (хуки, MCP, API-прокси), а не агент и по умолчанию
не маршрутизатор моделей. **Batch**, **Flex** и **маршрутизация моделей** — три
разных рычага стоимости. Эта страница фиксирует, что прокси делает сегодня, что
**запланировано** и как каждый из них взаимодействует с кешированием промптов.

Источник замысла: `ideas.md` (заметки об экономии токенов I-100/I-101), `docs/prompt-cache.md`,
`research.md` (sticky-маршрутизация / D9). Поведение, которое не подключено в
`src/proxy/`, помечено как **запланировано**.

## Три разные вещи

| Рычаг | Что это | Синхронный ход агента? | Переписывает тело? |
|-------|------------|------------------|--------------------|
| **Batch** | Асинхронные API провайдеров (`/v1/batches`, `/v1/messages/batches`, …) | Нет — отправка, опрос, получение результатов | **Pass-through** (без преобразования sync→Batch) |
| **Flex** | Те же синхронные эндпоинты, более дешёвый/медленный уровень через `service_tier` | Да | **Переписывание** в `prepare` (`[proxy.lanes.<lane>] flex`) |
| **Маршрутизация моделей** | Выбор более дешёвой модели для простых ходов (D9) | Да | **Переписывание** `model` только для вызовов `internal` и включённого `bulk` (`[proxy.routing]`) |

rtok **не** преобразует прозрачно живой `POST /v1/messages` агента (или
`/v1/chat/completions`) в задание Batch. Агентам нужен синхронный ответ на
том же HTTP-запросе; Batch — это отдельный клиентский процесс, который просто проходит
через тот же узел прокси.

MCP-инструменты и хуки Claude Code никогда не видят HTTP-трафик LLM — его видит только
прокси. Поэтому Batch/Flex/маршрутизация целиком живут в `rtok proxy`
(`src/proxy/`), а не в `src/hooks/` или `src/mcp.rs`.

## Pass-through и переписывание

Конвейер прокси для нестандартного запроса (`shape_request` в `src/proxy/mod.rs`):

1. **record** — строки `calls` / `call_io` (fail-open)
2. **compress** — только при `proxy.mode = "compress"`; запускает `Plugin::proxy_filter`
3. **tools_rewrite** — включается явно через `[proxy.tools_rewrite]`
4. **prepare** — формирование запроса под конкретный протокол (сегодня: OpenAI
   `stream_options.include_usage`; бета context-management у Anthropic, когда она активирована)
5. пересылка в upstream; ответ дублируется для разбора usage, когда подходит `Wire`

Неизвестные пути по-прежнему попадают в **fallback** axum и пересылаются провайдеру
побайтно идентичными. `Wire::matches` точно сопоставляет формы синхронного чата
(`/v1/messages`, `/v1/chat/completions`, `/v1/responses`, Gemini
`:generateContent`) — пути Batch сегодня **не** совпадают ни с одним протоколом, поэтому они пропускают
compress / prepare / разбор usage и ведут себя как простой обратный узел со
строкой `calls`, когда учёт включён.

| Класс путей | Сегодня | Задумано |
|------------|-------|----------|
| Протоколы синхронного чата | record + необязательные compress/prepare + usage | без изменений |
| Эндпоинты Batch | пересылка через fallback; нет `Wire`; нет строки usage | **запланировано**: наблюдение за жизненным циклом пакета + usage результатов |
| Flex (`service_tier`) | клиент может его задать | `prepare` задаёт его только в включённых lane и не перезаписывает клиентское значение без `[proxy.flex] force` |
| Маршрутизация моделей | один URL upstream; модель остаётся такой, какую отправил клиент | только вызовы `internal` и включённого `bulk`, по правилу оператора в `[proxy.routing]`; lane `agent` не маршрутизируется никогда |

## Эндпоинты Batch API

Batch провайдера — это асинхронный API, **инициируемый клиентом**. Направьте тот же базовый URL на
`rtok proxy`; fallback перешлёт путь.

### OpenAI

| Метод | Путь | Роль |
|--------|------|------|
| `POST` | `/v1/batches` | создать пакет из загруженного файла JSONL |
| `GET` | `/v1/batches/{id}` | опросить статус |
| `GET` | `/v1/batches` | список |
| `POST` | `/v1/batches/{id}/cancel` | отменить |
| (файлы) | `/v1/files` | загрузить вход / скачать выход (тоже пересылается через fallback) |

Поддерживаемые эндпоинты элементов пакета (документация провайдера): `/v1/chat/completions`,
`/v1/responses`, `/v1/embeddings` и другие. rtok не переписывает строки JSONL
внутри файла пакета.

### Anthropic

| Метод | Путь | Роль |
|--------|------|------|
| `POST` | `/v1/messages/batches` | создать Message Batch |
| `GET` | `/v1/messages/batches/{id}` | опросить |
| `GET` | `/v1/messages/batches` | список |
| `GET` | `/v1/messages/batches/{id}/results` | получить результаты потоком/скачать |
| `DELETE` | `/v1/messages/batches/{id}` | удалить (после отмены, если выполняется) |

Точное совпадение по `/v1/messages` означает, что `/v1/messages/batches…` никогда не попадает в
адаптер `Wire` для Anthropic — никакого `proxy_filter`, никакого внедрения context-management.

### Чем Batch **не** является

- Не заменой Flex на живом ходе агента.
- Не автоматикой: rtok не будет ставить синхронный трафик в очередь Batch (**запланированная**
  политика остаётся «никогда», если позже не будет спроектирован явно включаемый инструмент/CLI).
- Не виден хукам/MCP.

### CLI (включается явно)

Тонкий, **явно включаемый** интерфейс для людей/скриптов, которые уже работают с Batch провайдера, —
вне цикла агента. Он **не** заменяет `ANTHROPIC_BASE_URL` /
`OPENAI_BASE_URL` агента (они остаются на протоколах синхронного чата). Команды обращаются к тому же
узлу `rtok proxy` (`--url`, по умолчанию `[proxy] bind` и `port`) и **пропускают насквозь** пути
Batch провайдера (`/v1/batches`, `/v1/messages/batches`, …); без преобразования sync→Batch.

| Команда | Роль |
|---------|------|
| `rtok batch submit <jsonl>` | создать пакет из файла, где на строку приходится один запрос в формате провайдера |
| `rtok batch status <id>` | объект пакета, как его отдаёт провайдер |
| `rtok batch fetch <id> <out>` | результаты в новый файл `<out>` (существующий файл не перезаписывается) |

- Ключ читается только из `ANTHROPIC_API_KEY` / `OPENAI_API_KEY`; провайдер — `--provider`, иначе
  определяется по id (`msgbatch_…` — Anthropic).
- Anthropic: каждая строка — `{custom_id, params}`, строки уходят в `requests` байт в байт. OpenAI:
  каждая строка — `{custom_id, method, url, body}`; файл загружается с `purpose=batch`, затем
  создаётся пакет для единственного `url`, общего для строк (`completion_window` `24h`); `fetch`
  идёт по `output_file_id`.
- У путей OpenAI `/v1/batches*` и `/v1/files*` нет `Wire`; прокси отправляет их в
  `proxy.openai_upstream` (запрос с `anthropic-version` — это Files API Anthropic, он остаётся на
  `proxy.upstream`).

См. также `ideas.md` (бэклог экономии токенов I-100/I-101).

## Flex API (синхронный, более дешёвый уровень)

Обработка Flex в OpenAI — это тот же HTTP-интерфейс Chat Completions / Responses
с `"service_tier": "flex"` (документация провайдера). Задержка выше, цена
ниже; кеширование промптов на этом уровне может по-прежнему работать, если провайдер это
поддерживает.

**Сегодня:** если клиент уже отправляет `service_tier`, прокси пересылает его
без изменений (passthrough / compress не удаляют неизвестные поля на пути разбора протокола,
который сериализует тело заново, только если фильтр его изменил).

**Flex по lane:** `[proxy.lanes.<lane>] flex = true` (lane `bulk`, `internal`, `embeddings`, `meta`;
никогда `agent`) позволяет `prepare` задать `service_tier = "flex"` в двух протоколах OpenAI, а `[proxy.flex]`
настраивает поведение:

- поле добавляется, если клиент его не указал (или прислал `null`); остальные байты пересылаются как есть
- клиентские `"default"` / `"auto"` / `"priority"` / `"flex"` уважаются; `force = true` их перезаписывает
- при `429 Resource Unavailable` (ничего не списывается, по руководству OpenAI от 2026-10-08) решает
  `on_429`: `none` отдаёт ошибку клиенту, `backoff` повторяет на Flex с удваиваемыми паузами,
  `default` повторяет один раз с уровнем клиента, если `force` его заменил, иначе с `auto`.
  `Retry-After` в секундах удлиняет паузу (максимум 30 с); `408` не повторяется. Повторяется только уровень, заданный rtok.

Ключи и значения по умолчанию: [config.md](config.md#proxyflex).

У Anthropic нет аналога `service_tier`; Flex здесь означает OpenAI (и любого будущего
провайдера, который предоставит эквивалентное поле в `Wire`).

## Взаимодействие с кешем

См. также [prompt-cache.md](prompt-cache.md).

| Механизм | Batch | Flex | Примечания |
|-----------|-------|------|-------|
| **Кеш промпта** провайдера (точное совпадение префикса) | Зависит от провайдера; OpenAI документирует совместимость Flex и кеша; строки Batch JSONL — отдельные запросы | Те же правила префикса, что и для sync; sticky upstream по-прежнему важен | rtok не должен перетряхивать `system` / `tools` / живые ходы — для синхронного compress это уже так |
| Переписывание живой зоны **archive** в rtok | Неприменимо при создании Batch (нет `Wire` для Messages) | Как для sync, когда Flex идёт через Chat/Responses | Тела элементов пакета внутри файла не переписываются |
| **Семантический** кеш ответов (P31) | Должен быть выключен для создания/опроса Batch (**запланированная** защита) | Те же правила применимости, что и для sync | Попадание для агентов всё равно означает неверный ответ |

Sticky-маршрутизация (закрепление одного и того же пода/региона upstream за сессией) касается
**попаданий в кеш промпта**, а не выбора между Batch и Flex. Задания Batch асинхронны и обычно
не могут разделять живой KV сессии с интерактивным агентом; не рассчитывайте получить скидку Batch
**и** тариф чтения из кеша интерактивной сессии на одних и тех же байтах.

## Измерение / метрики

**Сегодня (синхронные протоколы):** каждый проксированный запрос может записывать `calls`, `call_io`,
`tokens` и `usage` (четыре счётчика). `rtok stats` / `rtok stats --price`
читают эти строки. Пути без `Wire` (Batch, `/v1/models`, …) записывают
вызов, когда учёт включён, но пропускают разбор usage (`src/proxy/mod.rs`).

**Lanes (T385.1):** каждый запрос относится к одной из lane (`src/proxy/lane.rs`), и его
`calls.kind` её записывает: `api_request` для `agent`, `api_request:<lane>` для `bulk`,
`batch`, `files`, `embeddings`, `meta` и `internal`. Путь определяет Batch, files,
embeddings и meta; `x-rtok-lane` или префикс `/lane/<name>/` выбирает `bulk` или `internal` для
синхронного вызова чата. Оба убираются перед пересылкой. См. `[proxy.lanes]` в
[config.md](config.md).

**Запланировано для Batch:**

- ~~помечать `calls.kind`, чтобы создание/опрос/результаты Batch можно было отличить от синхронного
  `api_request`~~ — сделано тегом lane (T385.1)
- ~~при получении результатов разбирать usage по строкам в строки `usage`~~ — `[proxy.batch]
  parse_results` (T385.4); `rtok stats --price` оценивает этот usage по строке `<model>@batch` в
  `[stats.prices]` (T385.12.1)
- показывать разбивку Batch / sync / Flex в `rtok report` / stats (T385.12.2)

**Запланировано для Flex:**

- записывать фактический `service_tier` в строку `calls` (T385.12.2)
- оценивать токены Flex по строкам `<model>@flex`, которые поставляются в `[stats.prices]` (у OpenAI
  Flex стоит по ставкам Batch); читать их начнут, когда уровень будет записываться

Пока это не реализовано, считайте экономию Batch/Flex числами из консоли провайдера, а не
числами журнала rtok.

## Конфигурация

Ключи ниже задокументированы для проектирования; бинарник их **пока не**
загружает — три таблицы существуют, но пусты, поэтому любой ключ не проходит `rtok config validate`. См. [config.md](config.md).

```toml
# Запланировано — сегодня не разбирается
[proxy.batch]
enabled = true          # пересылать пути Batch (сегодня через fallback всегда true)
observe = true          # записывать создание/опрос/результаты в журнал
parse_results = false   # если true, разворачивать файлы результатов в строки usage

[proxy.flex]            # работает, в отличие от остального эскиза
force = false           # overwrite a client service_tier
on_429 = "none"        # none | backoff | default
retries = 3             # backoff only
backoff_ms = 1000       # backoff only

[proxy.routing]         # live (правила по lane, см. config.md), в отличие от `sticky` ниже
enabled = false         # маршрутизация моделей (D9) вызовов internal / bulk; по умолчанию выключено
sticky = true           # запланировано: предпочитать один upstream ради привязки к кешу промпта (I-84)
```


## Маршрутизация моделей (отдельное направление)

**По включению, только lane `internal` и `bulk`** — не входит в MVP Batch/Flex. Решение **D9** /
`research.md` §16.3 #3: маршрутизация по задаче путём переписывания `model` в `[proxy.routing]`.
Lane `agent` не маршрутизируется никогда (маршрутизация ходов агента остаётся Later, за контролем
качества I-101). Sticky upstream (`sticky`, I-84, пока запланирован) — это привязка к кешу промпта,
а не выбор модели. Полный дизайн: [model-routing.md](model-routing.md).
