# Бенчмарки — інструкції для агентів

Після **кожного** запуску бенчмарку (тесту фікстур `tests/bench_fixtures.rs`, Docker/Colima-обгортки `bench/harness/run.py`, порівняння з конкурентом) у тій самій зміні оновіть усі місця, де наведено старі числа. Немає вимірювання — немає твердження: для відсутнього вимірювання вказуйте `no data`, ніколи не оцінюйте його.

## 1. Запуск

Завжди в Docker, ніколи на фізичній машині.

1. Colima (macOS): використовуйте профіль `rtok-bench` (4 CPU, 8 GiB). Вкажіть `DOCKER_HOST` як сокет профілю (`~/.colima/rtok-bench/docker.sock`); якщо помічник облікових даних дає збій, укажіть у `DOCKER_CONFIG` каталог із порожнім `credsStore`.
2. Обгортка: `python3 bench/harness/run.py rtk --rtok-ref origin/main --rtok-pr origin/<branch>`. Посилання мають розв’язуватися у вашому клоні (`origin/...`, а не лише назва гілки). Запуск триває 10 хвилин або довше: запускайте його у фоні й дочекайтеся завершення; закриття shell зупинить процес.
3. Результати зберігаються в `bench/harness/results/<tool>/<stamp>/` (`results.json`, `summary.md`, `negatives.txt`, `versions.json`, `samples/`). Вони відстежуються в репозиторії.
4. Тест фікстур: `cargo test --test bench_fixtures`. У контейнер передайте вихідні файли командою `tar --no-xattrs … | docker cp - <container>:/src` (розширені атрибути macOS ламають звичайний `docker cp`; bind-mount `/tmp` не спрацював).
5. Оновлюйте фікстури лише зі справжнього захоплення даних: `run.py rtk --refresh-fixtures <dir>`, потім скопіюйте їх у `tests/fixtures/bench`. Ніколи не редагуйте їх вручну. Після оновлення перевірте кожен `min_savings_pct` у `case.toml`.
6. Версії конкурентів закріплені в Dockerfile конкурента в `bench/harness/tools/`.
7. Диск: віртуальна машина Colima та каталоги Rust `target` швидко заповнюють диск. Збирайте в контейнері й видаляйте створені контейнери та тимчасові каталоги після завершення.

## 2. Де шукати числа

Шукайте, не вгадуйте: `rg -n "<old number>|bench/harness/results" README.md docs/`.

- `docs/comparison/rtok-vs-<tool>.md` — окрема сторінка для кожного конкурента.
- `docs/comparison/README.md` — покажчик зі статусом кожного конкурента.
- `docs/comparison.md` — підсумкові таблиці.
- `docs/research/competitors-techniques.md` — прогалини й цілі (цілі не є вимірюваннями).
- `plan.md` / `todo.md` — рядки завдань із цільовими значеннями.
- `README.md` — головні показники, якщо вони там є (на момент написання їх не було).
- `bench/harness/README.md` — команда відтворення та правила чесного порівняння, якщо змінювалися прапорці.
- `docs/ru/`, `docs/uk/` — переклади; синхронізуйте їх з оригіналом (див. `CONTRIBUTING.md`).

## 3. Структура сторінки (блоки вебсайту)

На кожній сторінці порівняння мають бути такі розділи `##` у вказаному порядку:

1. **Що змінилося** — дата запуску, SHA rtok, відмінності від попереднього запуску.
2. **Показники продуктивності** — підсумки для кожної команди: raw, rtok main, rtok PR, rtok PR `--no-ref`, конкурент.
3. **Таблиця команд** — окрема таблиця `###` для кожної команди, по одному рядку на випадок.
4. **Де rtok виграє / програє** — пункти з числами; наведіть кожен рядок `WARN NEGATIVE` і позначте випадки `nondet!`.
5. **Методологія** — SHA фікстур, версії інструментів, токенізатор, кількість запусків, каталог результатів.
6. **Загальний огляд конкурентів** та **Як повторити**.

## 4. Контрольний список

- [ ] Запуск виконано в Docker; шлях до каталогу результатів записано.
- [ ] `cargo test --test bench_fixtures` проходить.
- [ ] `negatives.txt` прочитано; кожен негативний результат зазначено в розділі «Де rtok виграє / програє».
- [ ] Старі числа знайдено пошуком і замінено в кожному файлі з розділу 2.
- [ ] SHA і версії інструментів збігаються з `versions.json`.
- [ ] Затримку не подано як швидкість фільтрації (основну частку додає shim відтворення).
- [ ] Англійський оригінал оновлено; переклади ru/uk синхронізовано або внесено до списку наступних задач.
- [ ] Тимчасові каталоги й контейнери видалено.
