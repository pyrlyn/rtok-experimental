# Агенты и рабочие деревья

Каждая сессия агента, которая работает через rtok, получает один **id агента rtok**, а каждое рабочее дерево (worktree) привязано к агенту, которому оно принадлежит, одинаково на всех хостах. Агенты и пользователь могут обмениваться сообщениями по этому id. Эта страница — описание для пользователя (решение D34); таблицы установки по хостам находятся в [agents.md](agents.md), а ключи конфигурации — в [config.md](config.md).

## Id агента

- Id — случайный UUIDv4, который rtok выдаёт сам; он показывается первыми 8 символами и принимается везде как любой уникальный префикс из 4 и более символов. Id сессий хостов не уникальны между хостами, а у нескольких хостов их нет вовсе, поэтому они никогда не используются как id.
- **Хуки** регистрируют агента при первом событии сессии и обновляют его при каждом следующем (`SessionStart`, вызовы инструментов, `SessionEnd`). Хосту, чья установка несёт хуки, больше ничего не нужно.
- **MCP** обслуживает хост без хуков. `rtok mcp --host <host>` связывает себя с агентом сессии по собственному id сессии хоста, если хост кладёт его в окружение (Grok Build: `GROK_SESSION_ID`), иначе по единственному живому агенту этого хоста в том же каталоге, замеченному с момента запуска процесса. Два кандидата не привязывают ничего, поэтому сообщение никогда не попадёт не тому агенту. Хост, который не может нести ни хуки, ни id сессии, получает собственную строку, которую регистрирует процесс MCP.
- Агент всегда определяется по сессии. Ни один инструмент не принимает аргумент агента или владельца, поэтому модель не может занять рабочее дерево или отправить сообщение от имени другого агента.
- `rtok agents whoami` печатает id (`RTOK_AGENT_ID`, который хук Claude Code кладёт в окружение сессии и приводит в строке контекста начала сессии; если его нет, как в десктопном приложении Claude, — агент сессии из `CLAUDE_CODE_SESSION_ID`); MCP `whoami` возвращает его вместе со способом привязки.

## Видеть агентов и говорить с ними

| Команда | Инструмент MCP | Что делает |
| --- | --- | --- |
| `rtok agents sessions [--all]` | `agents_list` | каждый агент с хостом, состоянием (`live`, `idle`, `ended`), активностью, статусом, занятыми рабочими деревьями и числом непрочитанных; `--all` добавляет завершённых |
| `rtok agents show <id>` | `agent_show` | один агент: хост, модель, id, родитель и субагенты, cwd, занятые рабочие деревья, статус, непрочитанные |
| `rtok agents status <text>` | `agent_status_set` | чем занят этот агент (не более 120 символов); пустой текст очищает статус |
| `rtok agents send <id> <text>` | `agent_send` | сообщение одному живому агенту (с ограничением размера); `--all-live` отправляет каждому живому агенту проекта отправителя; `--task <id>` (`task` в MCP) помечает сообщение задачей, о которой оно, например `A12` |
| `rtok agents inbox [<id>]` | `agent_inbox` | ваши собственные сообщения, от старых к новым, с пометкой «прочитано»; с id — очередь этого агента, ничего не помечая; `--task <id>` (`task` в MCP) читает переписку по одной задаче, остальное остаётся непрочитанным |

`[agents] idle` (по умолчанию 30 минут) решает, кто считается живым. `[agents] enabled = false` отключает регистрацию и доставку сообщений.

### Сообщения

- Хост с хуками получает новые сообщения **вставленными** в следующий промпт или результат инструмента, в рамке и в пределах `[agents] push_bytes`; остальное объявляется как `… and N more` и читается через `agent_inbox`. Любой другой хост **забирает** сообщения сам: строка начала сессии велит вызвать `agent_inbox`, а читают их инструмент MCP или `rtok agents inbox`.
- Безопасность: тело сообщения — это текст от другого агента или человека, но никогда не инструкция. Каждое приходит в фиксированной рамке, называющей id отправителя, управляющие символы удаляются, размер ограничен, и ни один аргумент инструмента не может назвать отправителя. Воспринимайте его как информацию.

## Рабочие деревья

Сырой `git worktree` не записывает ни владельца, ни возраст, ни размер. `rtok worktree` даёт каждому рабочему дереву одно место, одно имя, одного владельца и одного агента:

| Команда | Инструмент MCP | Что делает |
| --- | --- | --- |
| `rtok worktree add <task> [<slug>]` | `worktree_add` | создаёт `<root>/<repo>-<task>` на ветке `<task>[-<slug>]` от свежего `origin/<default>`, с блокировкой `<owner> \| <task> \| <date> \| agent <uuid>`, и записывает заявку |
| `rtok worktree adopt [<path>] [--task <id>]` | `worktree_adopt` | привязывает рабочее дерево, созданное хостом, к вызывающему агенту; каталог остаётся там, где его поставил хост |
| `rtok worktree claim <path>` | — | то же для существующего рабочего дерева, которое вы назвали; переписывает его блокировку, когда её нет, она уже ваша, или её агент завершён либо не был виден дольше `--stale-lock` (`7d`) |
| `rtok worktree list` | `worktree_list` | каждое рабочее дерево репозитория с владельцем, привязанным агентом и его состоянием, `origin`, размером исходников (`--sizes` обходит и билд-кеши); а также сироты, которые git больше не перечисляет |
| `rtok worktree remove <path\|task>` | `worktree_remove` | удаляет ваше собственное чистое рабочее дерево и его слитую ветку; отказывает для грязного, для неслитой ветки, для того, в котором вы стоите, и для чужой блокировки, кроме случая, когда задача завершена (слита, чиста, с собственными коммитами) или агент блокировки завершён либо не был виден дольше `--stale-lock` (`7d`); отказ называет, как давно видели держателя; никогда не форсирует |
| `rtok worktree finish [<path>]` | `worktree_finish` | передаёт рабочее дерево задачи на ревью: коммитит оставшееся (`-m`, иначе `<task>: <slug>`), пушит ветку, открывает PR или берёт уже открытый, просит squash auto-merge (`--no-auto-merge` пропускает; отказ — предупреждение), затем снимает блокировку; отказывает для основного checkout, detached HEAD, чужой блокировки, файлов с учётными данными вроде `.env` или приватных ключей и ветки, которой нечего передать; задачу никогда не закрывает. `--repo <owner/name>`, когда `origin` не называет репозиторий. Когда ветка слита, запущенный `rtok mcp` (проверяет раз в 5 минут) закрывает задачу rtok, затем удаляет чистое рабочее дерево, его ветку и привязку; не слитое или грязное остаётся |
| `rtok worktree gc`, `clean` | — | убирают завершённые рабочие деревья, удаляют простаивающие кеши сборки; пробные прогоны до `--yes`; рабочее дерево живого агента сохраняется, а если его задача завершена и простаивает дольше `--idle`, оно удаляется при любой блокировке; чужая блокировка на слитом чистом рабочем дереве, не тронутом дольше `--stale-lock` (`7d`), считается брошенной |
| `rtok worktree migrate` | — | переносит рабочие деревья репозитория, лежащие вне корня, в `<root>/<repo>-<task>` (дерево без блокировки сохраняет имя каталога) через `git worktree move`; блокировка и claim переезжают вместе с ним; без `--yes` это пробный прогон; пропускает основной checkout, дерево, в котором вы стоите, дерево с блокировкой или claim другого агента или с другой живой сессией, дерево с подмодулями и занятый целевой путь |

Владелец — это `<host> / <model>` агента, если вызов CLI не передаёт `--owner`; вызов MCP никогда его не передаёт. Без агента и без `--owner` (хук, который запускается раньше, чем у сессии появился id агента) владелец — это `RTOK_OWNER`, если переменная задана, иначе пользователь ОС (`USER`, `USERNAME`, иначе `unknown`), и rtok пишет предупреждение в stderr; такая блокировка не называет агента, поэтому держит, как любая блокировка без него. Корень — `[worktree] root`, по умолчанию `.rtok/worktrees`: относительный корень отсчитывается от основного checkout (и изнутри рабочего дерева тоже), а перед первым рабочим деревом там rtok делает так, чтобы git игнорировал `.rtok/`: в `.gitignore`, если он есть в проекте, иначе в `.git/info/exclude`. Относительный корень, выходящий за пределы проекта, отклоняется; `~` и абсолютные корни значат то же, что и раньше, а рабочие деревья, созданные в другом месте, продолжают работать. При `[worktree] enabled = false` rtok не трогает рабочие деревья: каждая команда `rtok worktree` (и `list` тоже) сообщает, что они не включены, MCP не перечисляет ни одного инструмента `worktree_*`, а хуки `WorktreeCreate`/`WorktreeRemove` Claude Code и CodeBuddy делают то, что хост делает без rtok. У Command Code своего запасного пути нет, поэтому его хук создания тогда делает простое рабочее дерево в `.commandcode/worktrees/<name>` на ветке `worktree-<name>` — так же, как когда rtok отклоняет имя.

Новое рабочее дерево начинает с прогретыми кэшами сборки. После `git worktree add` rtok заполняет каждую запись `[worktree] seed_dirs` (по умолчанию `target` и `node_modules`; голое имя совпадает и на уровень ниже, так что `web/node_modules` тоже считается) из соседнего checkout того же репозитория, который собирал её последним. Каждый файл — copy-on-write клон, где файловая система умеет делить блоки (APFS на macOS; btrfs, XFS и bcachefs на Linux; ReFS и Dev Drive на Windows), поэтому даже многогигабайтный `target/` почти не занимает места, а в остальных случаях — обычная копия, которая экономит сборку, но не диск. Каждый файл сохраняет время изменения исходника, поэтому cargo пересобирает то, что изменила новая ветка, и оставляет все зависимости; `touch` не нужен. Место, которое в checkout уже занято (отслеживаемый каталог, прошлый засев), не трогается, а ссылка никогда не бывает источником. Засев делается по возможности: при ошибке выводится предупреждение, частичная копия удаляется, а рабочее дерево всё равно создаётся. `rtok worktree add --no-seed` пропускает его один раз; `[worktree] seed = false` выключает его, в том числе для MCP `worktree_add` и хука Claude `WorktreeCreate`. Он выполняется до возврата команды, поэтому большой кэш, который приходится копировать, а не клонировать, занимает столько же времени, сколько копирование.

`worktree add` работает по принципу «всё или ничего». Перед запуском git он проверяет свободное место на томе, где появится рабочее дерево, и одной строкой отказывает, если свободно меньше `[worktree] min_free_mib` (по умолчанию 2048 МиБ; 0 отключает проверку). Если после этого что-то падает (git, например с `No space left on device`, или запись claim), rtok удаляет каталог, ветку и claim, созданные этим вызовом; ветка или каталог, существовавшие до вызова, остаются.

`worktree add` принимает задачу и имя ветки и одним аргументом: `rtok worktree add "T504 read-hook-same-path"` — это задача `t504` на ветке `t504-read-hook-same-path` (первое слово — id, остальное — slug, пробелы становятся дефисами). Если рабочее дерево этой задачи уже есть и заблокировано тем же владельцем (или агентом), команда печатает его путь и ничего не меняет, поэтому повтор уже выполненного add безопасен; рабочее дерево, которое держит кто-то другой, по-прежнему отклоняется.

### Рабочие деревья, которые хост создаёт сам

Хост, который создаёт рабочие деревья в собственном пуле (Cursor, Codex, Windsurf и Devin, Kilo, Claude Code, Conductor), не оставляет rtok права голоса в выборе места. Выполните `worktree_adopt` (или `rtok worktree adopt`) внутри него: rtok выводит `origin` из пути, берёт задачу из `--task`, иначе из старой блокировки, иначе из ветки, и привязывает его.

- Cursor, Codex и Windsurf/Devin сами удаляют рабочие деревья, чтобы уложиться в предел (около 25, 15 и 20). Переживает ли при этом git-блокировка, не подтверждено, поэтому усыновление там записывает заявку только в хранилище rtok и не пишет блокировку.
- Любое другое происхождение получает ту же блокировку v2, что и `worktree_add`.
- Рабочее дерево, заблокированное кем-то другим, не берётся, пока его агент в пределах `--stale-lock` (`7d`). Завершённый агент или агент, которого хранилище не видело дольше этого окна, не мешает `claim` и `adopt`; отказ называет, как давно видели держателя. Блокировка без агента или с агентом, которого хранилище не знает, по-прежнему держит дерево.
- Запуск `adopt` из скрипта после создания у хоста (Cursor `.cursor/worktrees.json`, Kilo `.kilo/setup-script`, Windsurf и Devin `post_setup_worktree`) — настраивается командой `rtok agents install <host> --project` (хосты `cursor`, `kilo`, `windsurf`, `devin`): она добавляет одну запись в файл проекта и больше ничего не трогает; `rtok agents uninstall <host> --project` её убирает. Без названного агента `adopt` привязывает единственного живого агента хоста этого пула, чей рабочий каталог — репозиторий, а если таких нет или их несколько, откладывает claim без агента и без git-блокировки; его завершает следующий `adopt` или `SessionStart` сессии, работающей внутри рабочего дерева; `worktree gc` такое дерево не трогает. Через навык ниже агент может усыновить всегда.

Навык `worktrees` сообщает агенту всё это: использовать `worktree_add` для новой работы, `worktree_adopt` для рабочего дерева, созданного хостом, `worktree_finish`, когда задача готова, `worktree_remove` после слияния.

### Десктоп-приложение Claude

Во вкладке Code десктоп-приложения MCP-инструменты rtok обслуживает один `rtok mcp`, который приложение запускает из `claude_desktop_config.json` для всех сессий сразу, а не процесс самой сессии. Этот процесс не находится ни под одной сессией и ни в одном её каталоге, поэтому MCP `whoami`, `worktree_*` и `agent_*` не могут понять, какой агент их вызвал, и отвечают «not linked to an agent session» с этой причиной. Там используйте `rtok agents` и `rtok worktree` из shell агента. Чтобы общая запись не скрывала собственный сервер сессии — задача T456.
